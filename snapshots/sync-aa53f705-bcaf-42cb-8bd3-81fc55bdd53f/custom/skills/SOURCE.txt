  caveman-review/     压缩版 code review：一行一条 finding
  caveman-commit/     Conventional Commits 压缩成只留意图
  caveman-compress/   把自然语言文件压成 caveman 体（含 scripts/，见下方⚠️）
  ... 上游 skills/ 下其余 caveman-* / cavecrew 未装
本地改动（1 处，仅 compress）：
  caveman-compress/scripts/compress.py —— 加了 DeepSeek 通路（见下）。
  其余 4 个 skill 原文照搬。

⚠️ caveman-compress 的 LLM 通路（本机改造，已实测）
   上游 call_claude() 只认 Anthropic：优先 ANTHROPIC_API_KEY + anthropic 包，
   否则回退 `claude` CLI。本机三者都没有 —— 所以在 compress.py 里**加了一条分支**
   （函数 `_dsh_deepseek_key()` / `_call_deepseek()`，以及 call_claude() 开头的
   DeepSeek 尝试），走本机已有的 DeepSeek key：
     key 来源  环境变量 DEEPSEEK_API_KEY → 否则读 $DSH_HOME/.credentials.yaml 的 refs 段
     端点      https://api.deepseek.com/chat/completions（与 dsh-llm-deepseek 一致）
     模型      CAVEMAN_DEEPSEEK_MODEL，默认 deepseek-flash
     输出上限  CAVEMAN_DEEPSEEK_MAX_TOKENS，默认 131072（上游 8192，见下方修正）
     依赖      仅 stdlib urllib（系统 python3 没有 requests，且 pip 被 PEP 668 挡）
   **分支是增量的**：设 CAVEMAN_PROVIDER=anthropic，或让 key 解析不到，
   就完全走回上游原逻辑。要恢复上游，删掉那三段即可（都有 "LOCAL PATCH" 注释）。

   本机模型事实（2026-09-19 实测，非推测）
   --------------------------------------
   · 本会话实际模型：provider=deepseek-official, model=deepseek-flash
     （来源：$DSH_HOME/storages/session_projcache/sessions/<本会话>.json 的
       record.rows.modelSelection.val.lastUsed）
   · 上下文窗口：1,000,000 tokens
     （来源：同一文件的 record.rows.contextPressure.val.contextWindow；
       亦见 dsh-llm-deepseek 的 DEFAULT_CONTEXT_WINDOW = 1e6，
       该插件 4 个目录模型 deepseek-flash / v4-flash / v4-pro / v4-flash-vision-exp
       全部使用这个值）
   · 本机单次输出上限：256,000 tokens（dsh-llm-deepseek DEFAULT_MAX_TOKENS）
   · API 别名实况（实测回显）：请求 deepseek-chat 或 deepseek-v4-flash，
     响应回显的都是 "deepseek-flash"；不存在的模型名直接 HTTP 400。
     所以本机就是 deepseek-flash，写 deepseek-chat 只是被别名兜住，有误导性。

   修正了一处会真出错的照抄（max_tokens）
   --------------------------------------
   上游给 Claude 用的是 max_tokens=8192。实测本机模型：
     13 KB 输入 → completion_tokens 5,644
     110 KB 输入 → completion_tokens 11,614
   即 8192 在 ~20-30KB 输入处就会硬截断。已改为默认 131072（用
   CAVEMAN_DEEPSEEK_MAX_TOKENS 覆盖），并在响应 finish_reason=="length" 时
   直接报错，避免截断被伪装成"校验失败、重试两次后放弃"。

   实测记录
   --------
   · 947 B  → 541 B，code block 原样保留，validation 一次通过，exit 0
     原文备份 $XDG_DATA_HOME/caveman-compress/backups/cc-test/memory.original.md
   · 13 KB  → 9.3 KB，3 个代码标记全存活
   · 110 KB → **偶发失败**：一次报 "changed preserved code marker 5"（fail-closed，
     文件未被触碰、没留备份），同参数再跑一次 6 个标记全存活。
     → 这是本机模型在长输入上的**稳定性**问题，不是上下文不够（110KB 只用了
     20,363 prompt tokens，离 100 万很远）。所以：500KB 的 MAX_FILE_SIZE 相对
     100 万上下文是**偏保守**的，但它防不住这个偶发；大文件请预期可能重跑。
   · 另外它是**原地覆盖**目标文件，只压 .md/.txt/.typ/.tex，不碰代码。

    注册表 `skill` 仍在宿主面。

缺陷 1：markitdown 包装脚本静默吞掉正文（已修）
  /root/projects/.dsh/tools/markitdown
  旧版把 NOISE 正则同时作用在 **stdout 和 stderr** 上，而 NOISE 含
  `onnxruntime|cpuinfo|Unable to load|WARNING: Since` 这类宽泛词 —— 正文里出现
  这些词时整行被删，**退出码仍是 0**。实测：一份整篇讲 onnxruntime 的 md，
  转换输出为空白。
  修法：过滤器只作用于 stderr（stdout 是转换结果，不再重定向、原样直通），
  并把匹配收窄成日志行形状 `\[[A-Z]:onnxruntime:` / `^Error in cpuinfo:` /
  `^onnxruntime (cpuid_info )?warning:`。
  回归：正文含 onnxruntime/cpuinfo 完整保留；噪声仍被过滤（stderr 残留 0 行）；
  真实 traceback 与退出码 0/1 原样透传。

缺陷 2：系统 Python 没有 CA 路径，caveman-compress 直接 SSL 失败（已修）
  现象：`python3 -m scripts <file>` → [SSL: CERTIFICATE_VERIFY_FAILED]
        self-signed certificate in certificate chain
  根因：**/usr/lib/ssl 目录根本不存在**，而那正是 Python 默认的
        openssl_cafile(/usr/lib/ssl/cert.pem) 与 capath(/usr/lib/ssl/certs)。
        /etc/ssl/certs/ca-certificates.crt 虽然被放回来了，但 Python 默认不看那里。
        （markitdown 的 venv 能联网是因为它自带 certifi，与系统无关 —— 所以
          "markitdown 能通"并不能推出"系统 Python 能通"，这点容易误判。）
  修法：mkdir -p /usr/lib/ssl &&
        ln -sf /root/projects/.dsh/tools/cacert.pem /usr/lib/ssl/cert.pem
        特意指向**持久目录**里的 CA 束而非 /etc，这样 /etc 被换掉也不受影响。
  ⚠️ /usr/lib/ssl 本身仍在容器 rootfs（/usr）里，app 更新后可能消失；
     消失后上面两行即可重建（写入 app 更新后的自检清单）。
  验证：系统 python urllib 请求 https://api.deepseek.com 返回 401
        （= TLS 握手已成功，只是没带鉴权）；
        compress 端到端 244 B → 126 B，validation 一次通过，exit 0，
        原文备份已落到 $XDG_DATA_HOME/caveman-compress/backups/。
